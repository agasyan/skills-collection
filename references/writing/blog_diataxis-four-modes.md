# Diátaxis in five minutes
Daniele Procida. Diátaxis. https://diataxis.fr/start-here/
Type: blog · Read: 2026-10-06

## Core idea
Documentation comes in four kinds (tutorial, how-to guide, reference, explanation), each serving a different need and written a different way. Blurring them causes most documentation problems.
Evidence: none cited

## Points
- **Tutorial.** A lesson that takes a learner by the hand through doing something; the goal is skill and confidence, not getting a task done.
- **How-to guide.** Practical directions for an already-competent user solving a real-world problem; it serves work, not study.
- **Reference.** Accurate, complete, neutral facts the user needs to act correctly, structured like the thing it describes, as a map is.
- **Explanation.** Context and background that answers "why"; it may take perspectives and serves study, not work.
- **The compass.** Ask two questions: does the content inform action or cognition, and does it serve acquiring or applying skill?
- **Don't blur.** Crossing the boundaries is "at the heart of a vast number of problems"; the named example is a tutorial overloaded with explanation.
- **Minimal explanation, then link.** In a tutorial, give one line of why ("we use HTTPS because it's safer") and link to the in-depth article.
- **One improvement at a time.** Look at the doc, pick one small improvement, make it, repeat.

## For writing docs
- Label each page as one of the four kinds before writing; split a page that serves two.
- Write how-to guides for a competent reader with a goal; leave the teaching to tutorials.
- Mirror the code's structure in reference docs (module, class, method).
- Cut explanation inside tutorials and how-tos to one sentence plus a link.
